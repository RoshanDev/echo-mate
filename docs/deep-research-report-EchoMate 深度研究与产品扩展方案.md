# EchoMate 深度研究与产品扩展方案

## 市场机会与定位判断

从公开产品看，EchoMate 周边市场已经很拥挤，但拥挤点主要在“生成回复”，不在“关系运营”。一类产品是典型的“截图→出回复”工具：WingAI 主打截图聊天或个人资料后生成回复，还在 2026 年加入了 iMessage Extension；ReplyAI、SnapReply、EasyReplies、Cue 也都提供“上传聊天截图、生成多条候选、调语气、一键复制”的相似能力。这个需求显然真实存在，但也说明“5 条候选回复”本身正在快速商品化，差异化空间有限。citeturn21view0turn25view0turn25view1turn25view2turn25view3

另一类产品是个人关系管理工具，也就是更接近 EchoMate 长期壁垒的方向。Dex 把“keep-in-touch reminders、notes、timeline”做成核心卖点，并公开写到已有 30,000+ 用户；Clay 的 Home 会把“今日该想到的人”集中展示，包括 Reconnect 推荐、生日提醒、来自笔记的提醒和新联系人；Covve 会处理特殊日期、漏掉的提醒、直接行动；Monica 则把“提醒重要日期、礼物、任务、关系记录”做成一个以隐私和自托管为卖点的开源 PRM，并公开展示了数万用户、数十万联系人和近 9 万条提醒。公开资料已经证明：**“记住人与事、在合适时间提醒、帮助持续联系”本身就是可成立的产品价值**，只是这些工具偏个人/职业网络管理，不是实时聊天副驾。citeturn12view3turn12view0turn12view2turn12view4turn26view2turn28view0

第三类是更广义的 AI 沟通层。SwiftKey 已经验证了“选中文本→改语气→替换/复制”的低摩擦入口；Gmail 的 Smart Reply 与 Contextual Smart Reply 证明“基于整段线程而不是单条消息来给建议”是有效的；Slack AI 证明“总结 DM/线程+给出来源引用”可以显著降低信息回忆成本；Grammarly 则把 tone detection、rewrites 与隐私控制做成了成熟的写作层能力。它们说明真正高频的 AI 沟通产品，不是独立打开一个“聊天生成器”，而是**在原工作流上叠一层轻量、可信、可复制的副驾**。citeturn13view0turn12view7turn12view8turn13view1turn13view3

因此，EchoMate 最值得押注的定位，不是“更会撩的回复器”，而是**“个人关系 CRM + AI 回复副驾”**：它既能在当下帮用户自然回复，也能记住明确提过的事情、在恰当时机提醒，并给出“下一步该不该推进”的判断。增长上，这条路线也比单纯回复生成更有留存潜力，因为它能像 Clay 的 Home、Dex 的 keep-in-touch、Monica 的 advance notifications 那样，持续制造“今天值得打开一次”的理由。citeturn12view0turn12view3turn28view0

## 用户核心 Jobs-to-Be-Done 与沟通原则

从关系沟通研究看，能长期提升关系质量的，不是“更华丽的话术”，而是更稳定的**被理解感、被回应感和边界感**。经典亲密关系研究把亲密感看作“自我披露 + 对方响应”的共同产物；哈佛健康的沟通建议指出，validation 会让对方感到被理解、被支持，并更愿意进入问题解决；Psych Central 也强调，不请自来的建议可能让人感到不安全；而推荐系统研究显示，过度个性化、用户不清楚系统为什么“知道这些”的时候，会显著提升 creepy 感，损害信任与平台态度。对 EchoMate 来说，这意味着产品必须默认：**先帮助用户做到真诚和恰当，再追求效率；先解释来源，再利用记忆；先低打扰，再做主动提醒。** citeturn17search1turn16view5turn16view6turn16view0

| 用户情境 | 用户真实任务 | 成功定义 | EchoMate 应承担的工作 |
|---|---|---|---|
| 刚收到一条不知道怎么回的消息 | 快速想到自然、像自己、不油腻的回复 | 不尬、不拖、能顺滑接住话题 | 生成候选回复 + 风险标签 + “下一行动”建议 |
| 对方提过考试、面试、加班、出差、生病 | 不要忘记 follow-up，也别提醒得太过 | 用户能在对的时间轻关心一次 | 从聊天里提取事件、到点提醒、给出低压跟进文案 |
| 对方提过偏好、禁忌、烦恼 | 记得住，但不要“背答案式聊天” | 回复自然地体现“你有在听” | 提取高价值记忆，并在相关场景轻提示 |
| 不确定该继续聊、收束、邀约还是别追问 | 减少误判窗口期 | 行动不冒进、不拖沓 | 输出“继续/收束/邀约/别追问”的建议，而不只给文本 |
| 害怕 AI 说话不像自己 | 维持稳定的人设和语气 | 对方不觉得说话风格突然变了 | 用用户风格画像约束候选回复 |
| 聊天降温、久回、冲突后 | 既不要自我脑补，也不要继续硬顶 | 降低过度解读和二次伤害 | 只给低置信度状态判断，并附“为什么这样判断” |

还有一个很重要的产品原则是：**EchoMate 的情绪雷达和阶段判断必须是“低置信、可解释、可反驳”的。** 一方面，研究显示更快的响应速度通常会提升连接感；另一方面，在浪漫关系文本沟通里，文本频率与响应性的意义强依赖关系情境，尤其远距离与非远距离关系表现并不一样，不能把“回得慢”直接等同于“没兴趣”。所以，EchoMate 可以把响应滞后、字数变短、主动提话题减少，作为“可能降温”的弱信号，但不能把它包成“她就是不想理你”的强判断。citeturn15search1turn16view4

基于以上研究和公开竞品，EchoMate 的设计原则建议固定为四条：**真实表达优先、建议优先于自动执行、来源可见优先于黑箱推断、敏感信息最小化优先于“知道更多”。** 这四条，既是产品边界，也是长期信任护城河。citeturn16view0turn6search2turn6search12

## 竞品与相邻产品调研

面向 EchoMate，最有参考价值的不是单个竞品，而是三组能力堆栈。

先看“截图回复器”这组。公开 App Store 信息显示，WingAI、ReplyAI、SnapReply、EasyReplies、Cue 都已经把“截图输入、候选回复、调语气、复制发送”做到了非常直接，个别还加上了 iMessage Extension、Share Sheet、Learn My Style、历史记录等功能。说明用户已经被教育：**他愿意为“别让我盯着输入框发呆”付费。** 但这些产品大多停留在“单次会话求助”，很少有真正强的长期记忆、时机关怀和关系状态运营。与此同时，它们的隐私口径差异很大：有的声明会追踪 Usage Data，有的声明不收集数据，有的声明本地处理；而 Apple 本身也说明 App Store 隐私标签基于开发者申报，且“linked to you”意味着数据可与用户身份、账户或设备关联。换句话说，**隐私透明不是营销句子，而要做成产品机制。** citeturn21view0turn25view0turn25view1turn25view2turn25view3turn8search0

| 赛道 | 代表产品 | 已验证需求 | EchoMate 可借鉴点 | EchoMate 不能照抄的地方 |
|---|---|---|---|---|
| 截图回复器 | WingAI、ReplyAI、SnapReply、EasyReplies、Cue | 用户确实愿意把截图交给 AI 换来即时回复 | 截图输入、候选回复、复制即走、轻量语气选择 | 不要停留在“一次性生成器”，也不要走强操控、强撩法术路线 |
| 典型产品表征 | WingAI 有 iMessage Extension；ReplyAI 有 tone/history/custom notes；SnapReply 强调 tone matching 和 Share Sheet；Cue 提供 OCR 与 5 次免费生成。citeturn21view0turn25view0turn25view1turn25view3 |  |  |  |

再看“个人关系 CRM/PRM”这组。Dex、Clay、Covve、Monica 的共同点非常清楚：人的关系不是靠“有空再想起来”，而是靠**被组织、被提醒、被回顾**。Dex 强调 keep-in-touch reminders 和 unified timeline；Clay 会在 Home 里把 Reconnect、生日、来自笔记的提醒等统合出来，还允许在 notes 里 @ 相关人物形成关系网络；Covve 会记录特殊日期、错过的提醒和可立即采取的动作；Monica 则更彻底，把生日、礼物、任务、关系图谱、advance notifications 和自托管隐私结合了起来。它们最值得 EchoMate 学习的，不是“联系人管理”，而是“**为什么今天值得联系她一次**”这件事的呈现方式。citeturn12view3turn12view0turn12view2turn12view4turn26view2turn28view2

| 赛道 | 代表产品 | 已验证需求 | EchoMate 可借鉴点 | EchoMate 需要补的空白 |
|---|---|---|---|---|
| 个人关系 CRM | Dex | 忙碌用户需要 keep-in-touch reminders、notes、timeline | “触达理由”比“联系人录入”更重要 | Dex 不做即时聊天候选与关系推进副驾 |
| 关系 Home Feed | Clay/Mesh | 每天需要一个统一入口看“今天该想到谁、为什么” | Reconnect、生日、提醒、来源统一到 Home | Clay 偏网络管理，不是中文聊天副驾 |
| 提醒行动化 | Covve | 用户需要 special dates、missed reminders 和直接行动 | 到点提醒后直接给可执行动作 | Covve 不是对话中实时介入 |
| 隐私自托管 | Monica | 一部分用户非常在意“我的关系数据归我” | advance notifications、自托管、不开广告、不偷看数据 | Monica 缺少即时生成回复与多模态聊天理解 |

最后看“AI 沟通层/键盘层”这组。SwiftKey、Gmail、Slack、Grammarly 已经把低摩擦交互路径跑通了：**选中→重写、上下文→回复、线程→摘要、答案→来源**。这组产品给 EchoMate 三个直接启发。第一，入口一定要在原路径里，而不是强迫用户跳去另一个大界面；第二，摘要和回复都应该建立在多轮上下文之上，而不是只看最新一条；第三，任何“我为什么这样建议你”的地方，都应该像 Slack AI 那样尽量给来源，而不是只给结论。citeturn13view0turn12view7turn12view8turn13view1

| 赛道 | 代表产品 | EchoMate 可以直接吸收的模式 |
|---|---|---|
| AI 键盘重写 | SwiftKey | 选中文本即改语气，Accept/Copy 两种出口 |
| 邮件上下文回复 | Gmail Smart Reply | 不只看一条消息，而是看整个线程 |
| 线程摘要与来源 | Slack AI | 多轮摘要、问答、来源引用 |
| 语气监测与重写 | Grammarly | tone detection、rewrite、用户控制何时运行 |

综合来看，EchoMate 的竞品空白非常明确：**目前几乎没有产品把“即时回复辅助”“基于聊天的长期记忆”“合时提醒”“关系阶段判断”“本地优先与不自动发送”这五件事真正组到一起。** 这就是 EchoMate 应该占住的位置。

## 三阶段产品路线

从可落地性看，EchoMate 现有 Tauri 架构已经非常适合走这条路线。Tauri 官方插件已经覆盖了全局快捷键、剪贴板、通知、SQLite、持久化 Store、Stronghold 加密与 AppData 文件系统；其中通知插件明确要求先拿到系统权限，剪贴板插件默认也不自动开放权限，正好符合 EchoMate 的“主动触发、明确授权、本地优先”原则。citeturn14view0turn14view1turn13view4turn13view5turn14view2turn13view6turn14view3

建议把产品路线拆成三段，而不是一次性做成“万能恋爱 AI”。

| 维度 | Phase 1：现有架构兼容、快速上线 | Phase 2：记忆与提醒系统成型 | Phase 3：长期关系副驾 |
|---|---|---|---|
| 核心目标 | 让当前回复弹窗“更有脑子” | 让 EchoMate 开始“记住并主动提醒” | 让 EchoMate 变成一段关系的长期操作层 |
| 关键能力 | 候选回复 + 下一行动建议 + 记忆候选卡 + 事件提醒建议 + 截图多轮摘要 | Home Feed、提醒中心、记忆中心、关系阶段卡、情绪雷达、事件 follow-up | 时间线总结、窗口预测、冷淡/冲突修复、偏好漂移、长期复盘 |
| 关键用户流程 | 触发快捷键 → 读取文本/截图 → 生成回复 → 顶部显示“值得记住”“何时提醒”“该继续还是收束” → 用户确认 | 本地通知到点 → 打开 EchoMate 小面板 → 看原文来源 + 当前状态 + 3 条推荐跟进 → 复制/稍后/忽略 | 每周或每次触发时，系统给出“本周值得做的一步”、阶段变化、邀约窗口和修复建议 |
| UI 入口 | 现有弹窗加 3 个区块：①当前判断 ②候选回复 ③记忆/提醒 chips；托盘菜单增加“她的记忆”“提醒列表” | 托盘/悬浮入口增加“今天”“记忆”“时间线”；通知点击进入“跟进面板” | 增加“关系看板/时间线”页面，但仍保持小工具为主 |
| 数据结构草案 | `fact_candidates`、`memory_items`、`reminders`、`context_summaries`、`reply_feedback` | 新增 `stage_snapshots`、`emotion_signals`、`reminder_rules`、`memory_sources`、`safety_prefs` | 新增 `weekly_summaries`、`interaction_features`、`stage_explanations`、`long_term_goals` |
| 成功指标 | 候选回复复制率、记忆确认率、提醒创建率、平均生成时延 | 提醒打开率、提醒后复制率、错过事件下降率、WAU/DAU、错误提醒删除率 | 30 天留存、每周有效互动数、用户手动查看 Home/时间线频次、越界投诉率 |
| 技术重点 | 只在用户触发时分析；SQLite 存事实与提醒；Store 存偏好；截图摘要先做本地缓存后清理 | 本地通知、提醒调度、记忆来源索引、敏感字段分级、Stronghold 管理密钥 | 增量总结、可解释状态机、反馈学习，不引入自动发送 |

关于“关系进展”，建议不要一上来追求学术上完整的十阶段模型，而是把 Knapp 的“关系逐步靠近 / 逐步疏离”思路压缩成 6 个**产品可执行阶段**。这样更适合真实聊天场景，也更容易和“下一行动建议”绑定。citeturn9search8turn9search2

|---|---|---|---|
| 刚认识 | 话题浅、轮次短、无未来计划 | 保持轻松、别查户口、别太快深聊 | 不要“上头式表白” |
| 轻熟悉 / 试探 | 出现互相接梗、轻自我披露、同日多轮互动 | 可以轻幽默、轻延展话题 | 不要过早上价值、不要审问式追问 |
| 稳定互动 | 双方都主动分享日常、会回到旧话题、会轻关心 | 可以做事件型 follow-up，开始记录偏好 | 不要每次都强行邀约 |
| 可邀约窗口 | 出现明确可用时间、积极回应物流型话题、未来指向 | 建议轻试探邀约，并给保守版话术 | 不要“今天立刻出来吗”式重推进 |
| 轻降温 | 回复变短、主动变少、但无明显敌意 | 减少追问，转低压关心或暂时收束 | 不要用慢回单一信号作结论 |
| 冲突 / 修复 | 负向情绪、误解、被冒犯、冷处理 | 先验证感受、澄清误会、别立刻讲道理 | 不要“解释型轰炸” |

这里最关键的工程约束是：**阶段判断必须附带“为什么这样判断”的理由**，比如“最近 7 天她主动开启 2 次话题”“出现了未来时间表达”“最近两次明确表达疲惫”，而不是只给一个神秘标签。Slack AI 已经证明“带来源的答案”比纯黑盒结论更容易建立信任，这个模式应该直接借过来。citeturn12view8

## 定时关怀、历史提醒与记忆系统设计

如果 EchoMate 要把“定时关怀”和“历史提醒”做成真正的差异化模块，最佳做法不是从“更多提醒”出发，而是从**提醒的证据、提醒的时机、提醒的边界**出发。公开产品已经给了几个很好的设计先例：Apple Reminders 会通过 Smart Lists 和来自 Mail/Messages 的建议项聚合待办；Todoist 把自然语言时间解析和 recurring reminder 做得很成熟；Notion 用 `@remind` 降低创建提醒的成本；Monica 则明确指出，生日类提醒不能只在当天提醒，而应该提前 30 天、7 天和当天多层提醒。EchoMate 应吸收这些模式，但一定要多加一步：**凡是来自聊天提取的提醒，都先让用户确认。** citeturn24view0turn24view1turn24view2turn24view3turn28view0

| 模块 | 触发条件 | 信息来源 | 默认提醒时机 | 提醒文案示例 | 用户确认方式 | 如何避免骚扰/越界 |
|---|---|---|---|---|---|---|
| 生日关怀 | 生日被手动录入，或高置信历史记忆已确认 | 用户手动保存 / 明确聊天记录 | 7 天前、当天 9:00 | “她生日快到了，要不要提前想一句祝福？” | `保存生日提醒` / `只当天提醒` / `不保存` | 不自动群发；不把生日当成强推进机会 |
| 考试 / 面试 | 聊天里明确提到“明天考试/周二面试” | 文本 / 截图 | 事件后 2–4 小时 | “她今天面试，今晚适合轻问结果，不适合追问细节。” | `今晚提醒我` / `改时间` / `忽略` | 默认只提醒一次；若用户未行动，不重复轰炸 |
| 加班 / 最近很忙 | 明确提到“这周都在加班/最近忙死了” | 文本 / 截图 | 24–72 小时后 | “她前两天说最近很忙，适合低压关心一次。” | `后天提醒` / `周末提醒` / `不需要` | 不每天追着提醒；若最近已发送多条消息则抑制 |
| 出差 / 旅行 | 明确提到出差或行程 | 文本 / 截图 | 出发前晚，返程后 +1 天 | “她明天出差，可以轻祝一路顺利；返程后再问一句累不累。” | 二选一或全选 | 不基于定位推断；不默认天气触发 |
| 生病 / 不舒服 | 明确提到感冒、发烧、不舒服 | 文本 / 截图 | 次日傍晚 | “她昨天说不舒服，今天问一句好点没会更自然。” | `明晚提醒` / `稍后提醒` / `忽略` | 不做医疗建议；不高频追问 |
| 情绪低落 | 明确表达“状态差/有点崩/心累” | 文本 / 截图 | 次日或 48h 后 | “她前晚状态不太好，今天适合轻关心，不适合讲道理。” | `明天提醒` / `仅记录` / `忽略` | 默认一次；不把情绪低落当邀约/推进机会 |
| 天气变化 | 仅在与既有事件或状态相关时触发，如她要早起赶路、近期感冒 | 用户已确认的事件 + 天气 API 可选 | 事件前夕 | “她明早要赶车，明天降温，可以提醒自己发一句注意保暖。” | 需用户开启“天气联动”总开关 | 关闭为默认；不做泛化天气骚扰 |
| 生理期 / 身体敏感期 | 只能由用户手动录入 | 手动 | 用户自定 | “按你设置的规则提醒你多点耐心/别安排高压互动。” | 仅手动开启 | 禁止 NLP 推断；默认不触碰 |

“历史提醒”模块建议做成**来源可见的记忆系统**，而不是一个越攒越恐怖的秘密档案。Slack AI 已经证明了“答案带来源”很重要；EchoMate 也应该让每条记忆都能回到产生它的原话、原截图摘要或原事件。这样用户既能纠错，也不会产生“它怎么知道这个”的不适感。citeturn12view8turn16view0

| 记忆类型 | 是否值得记 | 建议方式 | 过期策略 | 敏感级别 |
|---|---|---|---|---|
| 明确计划与时间点 | 很值得 | 自动候选，用户确认保存 | 事件结束后转历史 | 普通 |
| 稳定偏好 | 很值得 | 自动候选，用户确认保存 | 长期有效，可手动修正 | 普通 |
| 禁忌与边界 | 很值得 | 必须显示来源、确认后保存 | 长期有效，允许冻结 | 中 |
| 最近烦恼 / 压力点 | 值得 | 自动候选 | 7–30 天自动过期 | 中 |
| 关系节点（第一次见面、送过什么） | 值得 | 半自动 | 长期有效 | 中 |
| 健康细节、家庭矛盾、财务压力 | 谨慎 | 默认仅手动保存 | 手动管理，默认不自动提醒 | 高 |
| 生理期、住址、日常行动轨迹 | 原则上不自动记 | 仅手动且强确认 | 用户可一键删空 | 高 |
| 第三方秘密、密码、违法风险信息、性化细节 | 不该记 | 不保存 | 不适用 | 禁止 |

这里的设计底线应该直接遵守数据最小化与 privacy by default。英国 ICO 对 data minimisation 的说法非常明确：只保留完成目的所必需的最少个人数据；privacy by default 也要求每一个目的都只使用必要信息。NIST 的隐私工程框架则把 predictability、manageability、disassociability 作为核心目标——放到 EchoMate 上，就是要让用户知道存了什么、为什么存、怎么改、怎么删，而且默认不多采。citeturn6search2turn6search12turn6search3

所以，定时关怀与历史提醒的共通规则应当是：

1. **只抓明确表达或重复表达**，不要从模糊语气和脑补做强推断。
2. **保存前先确认**，尤其是健康、家庭和身体相关信息。
3. **每条记忆必须有来源**，且支持一键删除。
4. **每个事件默认最多一到两次提醒**，不要形成骚扰循环。
5. **绝不自动发消息**，只能提醒与建议。
6. **带 quiet hours、冷却时间和“近期已联系则抑制提醒”规则**。
7. **敏感信息默认加密、默认不参与普通生成。**

## 场景演练、禁区清单与最高优先 MVP

下面这 10 个场景，基本覆盖了 EchoMate 第一阶段到第二阶段最常见、也最值钱的实际使用时刻。

| 真实场景 | EchoMate 应该做什么 | EchoMate 不该做什么 |
|---|---|---|
| 她说最近很忙 | 给低压回复候选，并建议 2–3 天后轻 follow-up | 不要立刻建议“那见面放松一下” |
| 她提到明天考试 | 弹出“要不要记提醒”，并在考试后给跟进文案 | 不要第二天早中晚连发三次提醒 |
| 她说感冒了 | 建议轻关心并次日晚提醒一句好点没 | 不做医疗建议，不催喝药打卡 |
| 她隔了很久才回 | 给“别把慢回直接解读成冷淡”的提示，并建议收束或轻接住 | 不要上来输出“她没兴趣了” |
| 她主动分享照片 | 提供夸赞型和延展型两类回复 | 不要过度夸外貌、不要高速暧昧升级 |
| 聊天快冷掉 | 提供“自然收束”与“轻换题”两条路线 | 不要强行丢十个新话题 |
| 想约出来但不确定时机 | 结合最近互动强度给“可轻试探 / 再等等”的建议 | 不要把每次顺利聊天都当邀约窗口 |
| 她说今天去面试/出差/加班 | 帮用户记下，并在合适时点给一句跟进建议 | 不要在事件进行中频繁打扰 |
| 她说最近状态不好、想静一静 | 建议验证感受、降低话密度，并设置较晚 follow-up | 不要推荐“继续追问她怎么了” |
| 刚发生一点误会 | 优先给修复型表达和停火型建议 | 不要输出现长篇解释或辩论模板 |

哪些功能**不应该做**，建议明确写进产品边界与设置页里，因为这会直接影响口碑、合规和长期留存：

| 不该做的功能 | 原因 |
|---|---|
| 自动发送消息 | 会直接跨过用户意志，是最高风险的关系破坏点 |
| 偷偷扫描微信数据库、常驻监听所有聊天或所有剪贴板 | 与本地优先、主动触发原则冲突，也极易引发严重隐私问题 |
| 自动推断生理期、病史、家庭矛盾、定位规律 | 这类推断最容易造成 creepy 感，且不符合最小化原则 citeturn16view0turn6search2turn6search12 |
| “她对你兴趣值 83 分”“征服概率”之类的评分系统 | 会把产品带向操控、物化和伪确定性判断 |
| PUA 话术库、冷暴力策略、控制节奏技巧 | 与 EchoMate 的尊重、边界、真实表达目标冲突 |
| 编造用户没说过的话、没做过的承诺 | 会制造前后矛盾，长期一定翻车 |
| 高频复活僵尸会话的催发器 | 容易把“提醒”做成骚扰工具 |
| 未经明确同意把截图或聊天上传云端长期保留 | 与本地优先定位相矛盾，也削弱信任护城河 |

结合现有能力，**最高优先级 MVP** 很明确：不是再多做几种语气，而是做一个**“事件型记忆提醒 MVP”**。

这个 MVP 的定义可以非常聚焦：

| 项目 | MVP 设计 |
|---|---|
| 产品目标 | 让用户“不再错过明确窗口”，同时保持现有低打扰体验 |
| 解决的问题 | 她提到过重要事情，但用户忘了；或者记得有事，却不知道怎么在合适时间开口 |
| 核心流程 | 用户触发快捷键 → EchoMate 读取文本/截图 → 生成 5 条候选回复 → 同时提取 `事件/偏好/禁忌` 候选卡 → 用户点击“记一下/今晚提醒我” → 到点发送本地通知 → 打开小面板，显示来源、当前建议、3 条跟进候选 |
| UI 变化 | 在现有弹窗顶部加三块：`当前适合做什么`、`可能值得记住`、`提醒建议`；托盘里加 `今天` 和 `记忆` |
| 最小数据结构 | `memory_item(id,type,value,source_kind,source_ref,confidence,sensitivity,expires_at,status)`；`reminder(id,memory_id,trigger_at,reason,status,snooze_count)`；`context_summary(id,source_ref,summary)`；`reply_feedback(id,generation_id,action)` |
| 安全边界 | 仅用户触发分析；仅用户确认后保存；仅本地存储；仅本地通知；绝不自动发送 |
| 技术实现 | 用 Tauri 的 global-shortcut、clipboard、notification、sql、store、stronghold、fs；数据放 SQLite，小型偏好放 Store，敏感密钥交 Stronghold，截图缓存放 AppData 并可解析后删除。citeturn14view0turn14view1turn13view4turn13view5turn14view2turn13view6turn14view3 |
| 明确不做 | 多联系人 CRM、自动导入历史聊天、自动判断生理期、自动发消息、复杂关系评分系统 |
| 建议成功指标 | 候选回复复制率、提醒创建率、提醒打开率、提醒后复制跟进率、错误提醒删除率、越界/不适反馈率 |

为什么这个 MVP 优先级最高？因为它同时满足四件事。
第一，它和现有 EchoMate 架构完全兼容，不需要推翻当前“快捷键 + 剪贴板/截图 + CLI Provider + 候选弹窗”的工作流。第二，它比单纯回复生成更接近真正壁垒：**记住她说过什么，并在合适时间提醒你。** 第三，它比复杂的关系评分或情绪推断安全得多，因为它主要基于明确事件和用户确认。第四，它天然会形成留存循环：用户越确认记忆，提醒越准；提醒越准，回访越高；回访越高，回复副驾也越好用。换句话说，**EchoMate 的真正壁垒不是“我能帮你回一句”，而是“我帮你成为一个更有记性、更有分寸、更不容易错过窗口的人”。**
