# EchoMate 下一轮开发发现记录

创建时间：2026-06-09  
来源报告：`docs/deep-research-report-EchoMate 深度研究与产品扩展方案-2026-06-09.md`

## 产品判断

- EchoMate 不应该继续定位成“更会说话的话术工具”，而应推进为本地优先的“单联系人关系 CRM + AI 回复副驾”。
- 最优 MVP 闭环不是微信机器人，而是在现有热键、剪贴板、截图、候选弹窗上补齐：结构化摘要、记忆候选、提醒引擎、下一行动建议。
- 长期壁垒来自“记住重要窗口，并在合适时间提醒”，不是堆更多候选回复。
- 所有能力都应保持用户确认后再发、用户确认后再记、本地优先、可解释、可删除。
- 用户需要一个地方补充聊天记录之外的联系人资料，例如出生年份、籍贯、现居/工作城市、职业背景；这些资料应作为“用户手动补充事实”存储，不伪装成聊天内容。

## 报告中的高优先级功能

- Phase 1 优先：候选回复 + 下一行动、记忆候选抽取、一键创建 follow-up 提醒、单联系人关系卡、上下文摘要卡、风格画像、断点恢复、关怀模板库、提醒节流、导出/删除中心。
- Phase 2 适合后置：关系阶段徽标、情绪雷达、历史提醒流、禁忌与边界卡、多截图拼接理解、邀约时机建议、记忆去重与 TTL。
- Phase 3 再评估：官方微信只读提醒、历史导入、跨设备加密同步。

## 当前代码与近期问题带来的约束

- 截图保存时间和聊天真实时间不能混用。用户现在可能下午聊天、晚上截图，模型必须知道“截图捕获时间不是消息时间”。
- 白名单联系人清除上下文必须真的清掉消息、摘要、记忆、提醒、候选和 provider run，否则会出现测试话题污染真实联系人。
- e2e/mock 数据不能出现在真实用户画像、真实联系人上下文、真实 DB 中。测试必须使用 temp HOME/temp DB。
- “风格画像”只统计样本数和平均字数没有实际价值。下一步必须输出可操作规则，例如长度区间、禁用表达、emoji 倾向、低压/正式/调侃倾向。
- “找话题”需要先判断最后一条消息的新鲜度和来源可信度。时间不明时应给保守续聊策略，而不是假装对方刚说完某个话题。
- 手动补充资料需要 EchoMate 自己判断存储点和使用位置。合理做法是先调用 Claude Code 或 Codex CLI 把自然语言归类为结构化 `contact_facts`，再由本地检索/引用策略决定是否进入本次 prompt。
- Provider 失败需要更清晰的技术诊断。空输出、非 JSON、schema drift、stderr 都应进入可读错误，而不是只显示 `Keys: []`。

## 风险

- 上下文污染风险最高：如果旧测试数据或错误记忆进入真实联系人，用户信任会直接崩掉。
- 时间误判会让建议非常违和：晚间截图不等于晚间聊天，历史截图不等于当前窗口。
- 记忆过度会显得 creepy：未确认候选、敏感信息、第三方隐私都不能默认长期保存。
- 手动资料过度引用也会违和：例如知道“A 市人/在 B 市工作”不代表每次找话题都要提 A 市或 B 市，必须基于当前聊天场景相关性引用。
- 微信集成风险高：实时监听会改变产品心智，应作为官方只读实验，不进入当前主线。
- 自动化程度越高，越需要来源解释和用户确认，否则会滑向代聊和隐私失控。

## 决策

- 新建独立活动计划 `.planning/2026-06-09-next-product-round/`，不覆盖根目录历史计划。
- 下一轮先做 Phase 1 上下文完整性，而不是直接扩展更多候选回复。
- 截图理解、手动资料补充、记忆治理、提醒引擎按顺序推进；微信只读通道暂时 deferred。
- 手动补充资料进入 `contact_facts` 或同等结构化事实表，带 `fact_source=manual`、敏感度、TTL、引用策略和来源说明；不进入消息表。
- 所有测试和演示数据必须与真实用户数据隔离。

## 待澄清但不阻塞

- 应用级加密的密钥存储策略：系统 keychain、用户口令，还是先做未加密 schema 加上后续迁移。
- 风格画像先做全局还是联系人级例外：计划默认先做全局，后续再加联系人例外。
- 多截图输入的交互形式：批量选择、连续框选，还是截图收件箱。
- 手动资料归类优先用规则、本地 prompt，还是统一交给当前 provider CLI；计划默认先走 provider CLI 结构化，后续再加入规则 fast path。
- 关系阶段和情绪雷达是否进入首个可发布版本，还是只作为内部信号辅助生成。
