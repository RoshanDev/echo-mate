# EchoMate 下一轮产品开发计划

创建时间：2026-06-09  
参考来源：`docs/deep-research-report-EchoMate 深度研究与产品扩展方案-2026-06-09.md`  
当前状态：Phase 2-7 核心实现已接线并通过本地测试；多截图完整交互和候选编辑体验留作后续精修

## 目标

把 EchoMate 从“截图/剪贴板生成回复”推进到“本地优先的单联系人关系副驾”：它必须能解释自己用了哪些上下文、区分截图时间和真实聊天时间、支持用户手动补充对方资料、只保存用户确认过的记忆，并在合适时机给出低打扰的回复、下一行动和 follow-up 提醒。

## 硬边界

- 不自动发送消息，只提供建议、复制、提醒。
- 不做隐蔽后台监控，不默认扫描全量聊天历史。
- 不把 e2e、mock、测试联系人、测试话题写入真实用户上下文。
- 不默认长期保存敏感健康、性、财务、住址、第三方隐私等信息。
- 不在来源不明确时编造上下文，不把截图保存时间当作聊天发生时间。
- 不把用户手动补充的联系人资料伪装成聊天记录；引用时必须标明“用户手动补充”或对应事实来源。
- 不优先做微信机器人。未来只评估官方通道的只读提醒实验模式。

## 规划依据

研究报告给出的最高价值闭环是：候选回复 + 下一行动、记忆候选、follow-up 提醒、单联系人关系卡、上下文摘要、风格画像。结合近期本地排查，下一轮必须先补上上下文可靠性底座，否则记忆和提醒会继续被污染，候选回复也会出现“面试/粽子”这类驴唇不对马嘴的问题。

## Phase 1：上下文完整性与来源追踪

目标：让每次生成都能回答“用了什么、来自哪里、什么时候产生、能不能信”。

任务：

- [x] 设计并迁移来源模型：`source_contexts`、`suggestion_runs`、`message_events`、`memory_candidates`、`contact_facts` 统一记录 `contact_id`、`provider`、`input_kind`、`fact_source`、`created_at`、`captured_at`、`visible_message_time`、`inferred_chat_time`、`source_confidence`。
- [x] 区分四类时间：本地保存时间、截图捕获时间、截图内可见时间、真实聊天事件时间；真实时间不确定时必须标记 `unknown` 或 `inferred`。
- [x] 主弹窗显示上下文来源卡：当前截图/剪贴板、白名单本地摘要、用户手动补充资料、已批准记忆、候选记忆、提醒上下文分别列出。
- [x] 生成 prompt 合同新增“禁止使用未列出的背景信息”和“时间不确定时不得按当前时刻续聊”规则。
- [x] 清除联系人上下文需要覆盖消息、摘要、候选、记忆、提醒、provider run、截图来源缓存，并写回归测试。
- [x] 所有 e2e/mock 流程强制 temp HOME/temp DB，真实 DB 中发现 `e2e`、`mock`、测试联系人时测试失败。
- [x] Provider JSON envelope 解析增加空输出、stderr、非 JSON、schema drift 的可诊断错误，避免只显示空 keys。

验收：

- 清空联系人后，下一次生成不能再引用旧话题、旧测试内容或已删除记忆。
- 截图里只有“昨天下午/昨天 22:53”这类可见时间时，UI 和 prompt 都明确显示时间可信度，不把截图操作时间当作聊天时间。
- 任意候选回复都能追溯到具体来源卡，手动资料不会被展示成聊天原文。

## Phase 2：截图对话理解 v2

目标：把单张截图理解升级为可解释的对话事件提取，减少 OCR、左右角色、时间线和图片气泡误判。

任务：

- [x] 定义截图解析输出 JSON：`turns[]`、`speaker`、`text`、`media_kind`、`visible_time_label`、`bbox`、`confidence`、`warnings[]`。
- [x] macOS 优先接入 Apple Vision 本地 OCR，低置信度或复杂图片气泡才走视觉模型补偿。
- [x] 左右气泡识别不再只靠固定位置，结合头像列、气泡颜色、文本边界和 UI 截图方向。
- [ ] 支持多截图按选择顺序拼接，并提示跨图时间断点。
- [x] 对图片/表情/引用消息只做占位和说明，不把图片内容臆测成文本事实。
- [x] UI 展示“识别到的最后一条可回复消息”和“是否过期/是否适合现在接”。

验收：

- 对用户提供的微信聊天截图能正确识别左右角色和最后一条可回复内容。
- 下午聊天、晚上截图的场景中，找话题不会直接假设“刚刚说了粽子”。
- OCR 低置信度时，候选回复降级为保守建议或要求重新截图，不乱编。

## Phase 3：记忆候选、手动资料与记忆治理

目标：只让用户确认过、可解释、可删除、会过期的事实进入长期记忆；同时给用户一个入口补充聊天记录之外的对方资料，并让 EchoMate 判断如何存储和何时使用。

任务：

- [x] 模型输出 `memory_candidates[]`，字段包含 `type`、`summary`、`source_quote`、`confidence`、`sensitivity`、`ttl_days`、`reason`。
- [ ] 新增记忆候选收件箱：默认不保存，用户可记住、忽略、编辑、设过期时间。
- [x] 新增联系人资料补充入口：用户可用自然语言或表单录入“93 年、天津人、在上海工作”等聊天记录之外的信息。
- [x] 对手动补充内容调用 Claude Code 或 Codex CLI 做结构化归类，输出 `contact_facts[]`，字段包含 `fact_type`、`value`、`normalized_value`、`source_note`、`sensitivity`、`confidence`、`ttl_days`、`usage_policy`。
- [x] 手动事实按类型存储：身份背景、城市/地域、职业/工作地、长期偏好、禁忌边界、重要日期、临时状态分别进入不同检索策略，不直接混进聊天消息表。
- [x] 引用决策由 EchoMate 执行：生成时根据当前任务、最后聊天时间、事实类型、敏感度、相关性和新鲜度决定是否放入 prompt；无关事实不得为了“显得懂她”而硬引用。
- [x] 增加记忆去重和 TTL：事件类到期后自动降权，长期偏好可续期，敏感信息默认不建议保存。
- [ ] 每条已保存记忆都能查看来源、最后使用时间、被哪些建议引用过。
- [x] 设置页加入“数据审计”：按联系人查看消息、摘要、记忆、提醒、候选、provider runs，并支持一键清除。

验收：

- 未经用户点击确认的候选记忆不会进入长期上下文。
- 用户手动补充的联系人资料可被结构化保存、编辑、删除，并显示“用户手动补充”来源。
- 对“齐齐 93 年、天津人、在上海工作”这类资料，EchoMate 能识别为身份/地域/工作地事实；在闲聊、邀约、城市话题、节假日回家等场景可用，在无关场景不强行引用。
- 记忆列表没有 e2e/mock/测试内容。
- 候选回复引用记忆时，UI 能显示“为什么用了这条”。

## Phase 4：提醒与 follow-up 引擎

目标：从“识别到时间窗口”到“低打扰地提醒用户做下一步”形成闭环。

任务：

- [x] 设计提醒 schema：`contact_id`、`kind`、`due_at`、`source_memory_id`、`source_context_id`、`cooldown_key`、`status`、`snooze_until`。
- [x] 支持从当前上下文创建提醒草案，用户确认后入库。
- [x] 实现提醒中心：完成、延后、删除、静默联系人、静默提醒类型。
- [x] 系统通知到点后打开 EchoMate，并生成 3 条 follow-up 候选。
- [x] 加入频率控制：同一联系人每天最多 1 条主动提醒、每周最多 2 条；连续忽略后降频。
- [x] 对过期话题标记 stale，不把很久前的截图话题当作当前聊天。

验收：

- “明天面试/周末出差/感冒 48 小时后问候”等场景能生成提醒草案。
- 不会连续追问、不自动发送、不在无关时刻炫耀记忆。

## Phase 5：回复 + 下一行动生成 v2

目标：候选回复不只像一句话，还要知道当前该继续聊、收束、等待、创建提醒还是记住信息。

任务：

- [x] 统一模型输出：`situation`、`action`、`source_summary`、`reply_candidates[]`、`memory_candidates[]`、`reminder_candidates[]`、`warnings[]`。
- [x] 候选回复按意图分组：稳妥、轻松、幽默、收束、邀约、支持。
- [x] 生成前先判断最后一条消息距离真实聊天时间的可信度；不可信时优先给“续聊策略”而非假装当前对话刚发生。
- [x] 加入关系阶段和情绪信号，但只输出弱判断 + 置信度，不做读心式结论。
- [x] 针对“找话题”增加 grounding 规则：必须来自当前截图、已批准记忆、用户手动补充资料或用户主动输入，不允许 provider 自带测试语料。
- [x] 对手动资料加入引用解释：例如“引用：用户手动补充 - 天津人/上海工作”，并允许用户一键禁止本次使用。

验收：

- 候选回复和“当前适合做什么”一致，不出现来源冲突。
- 找话题会考虑最近一条消息的实际时效；时间不明时给低风险续聊或建议重新截图。

## Phase 6：关系卡与风格画像 v2

目标：把“画像”变成可操作的约束，而不是无用的统计摘要。

任务：

- [x] 单联系人关系卡展示：最近停在哪、用户手动补充资料、已批准记忆、待处理提醒、禁忌边界、互动节奏、历史建议。
- [x] 关系卡提供“补充资料”编辑区，支持自然语言输入、结构化预览、确认保存、删除和重新归类。
- [x] 风格画像从“平均字数/样本数”升级为规则：常用语气、禁用表达、长度区间、emoji 习惯、低压/正式/调侃倾向、示例句。
- [x] 样本来源只使用用户采纳或明确导入的内容，测试回复和 mock 回复不进入画像。
- [x] 设置页提供手动刷新、重建、清空风格画像，并显示本次画像依据。
- [x] 支持全局风格和联系人例外，但默认先做全局风格，避免过早复杂化。

验收：

- 用户能看懂画像对生成有什么实际影响。
- 刷新画像不会引入 e2e/mock/测试文案。

## Phase 7：隐私、日志与发布硬化

目标：发布前把数据控制权、日志边界和安装可信度补齐。

任务：

- [x] 首次启动隐私向导：说明本地存储、模型调用、截图外发、日志开关。
- [x] 日志默认不记录聊天正文；调试日志需二次确认并可一键清理。
- [x] 数据导出/清空中心支持全量清除、单联系人清除、记忆/提醒单项清除。
- [x] GitHub Actions 构建 macOS/Windows 包，macOS 签名与 notarization 另列 release gate。
- [x] Tauri shell/CLI 调用白名单审计，前端不直接持有 shell 能力。

验收：

- 用户能明确知道 EchoMate 存了什么、上传了什么、如何删除。
- 发布包不依赖真实用户数据库或本机临时状态。

## Deferred：微信官方只读提醒实验

仅在上面闭环稳定后评估。范围限制：

- 只考虑腾讯官方 ClawBot/iLink 通道。
- 默认关闭，实验室入口，明显状态提示。
- 只读提醒，不自动回复。
- 白名单联系人，默认不保存全文，只存极简事件摘要。
- 首次启用必须说明消息会经用户配置的第三方 AI 通道处理。

## 六周建议排期

- Week 1：Phase 1 上下文完整性、provider JSON 合同、清除语义和测试隔离。
- Week 2：Phase 2 截图解析 v2、时间语义、来源卡 UI。
- Week 3：Phase 3 记忆候选收件箱、联系人资料补充入口、确认入库、去重与 TTL。
- Week 4：Phase 4 提醒中心、系统通知、follow-up 草案。
- Week 5：Phase 5 回复 + 下一行动 v2、找话题时效判断、关系/情绪弱信号。
- Week 6：Phase 6/7 风格画像 v2、数据审计、隐私向导、发布硬化。
